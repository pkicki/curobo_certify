# CPU interval reference assumptions

The reference backend encloses real operations on exact binary64 inputs, assuming IEEE-754 binary64 round-to-nearest, ties-to-even; `math.nextafter` returns the adjacent representable number; Python arithmetic does not use fast-math or reassociation; and no external native extension substitutes arithmetic. Each primitive add/subtract/multiply/divide is expanded by one adjacent representable value. Exact rational constants are first enclosed by directed comparisons against the represented binary64 rational. Indeterminate operations (including zero times an unbounded interval) become the whole real line; division by any interval containing zero is rejected.

These assumptions are part of the proof contract, not a claim about all Python builds or processors. `scripts/audit_cpu_interval.py` has been run on Linux x86_64, glibc 2.31, CPython 3.12.4 (Anaconda GCC 11.2.0), with `sys.float_info.rounds == 1`. The artifact `runs/cpu_interval_runtime_audit.json` records 20,000 seeded exact-Fraction enclosure checks each for add, subtract, multiply and divide and no observed under-enclosure. Its status is `PASS_TESTED_ASSUMPTIONS`, not universal proof: it does not establish compiler flags, all exceptional cases, every input or another runtime. No native-linked trajectory certificate has been issued; the real Panda K3 outcomes are conditional serialized-model results while adapter jerk parity remains failed.

For point-valued polynomial inputs, power-to-Bernstein conversion is performed as an exact `Fraction` linear transform and each resulting rational is enclosed once. Nondegenerate interval-valued inputs use interval operations throughout. Exact zero addition and multiplication identities return zero/unchanged enclosures; this is exact set arithmetic and preserves endpoint zeros. Python integer inputs are interpreted as exact integers rather than rounded through binary64. These refinements avoid losing exact endpoint conditions without narrowing any non-point interval.
